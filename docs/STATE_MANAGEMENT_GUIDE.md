# State Management & Reactivity Guide

**Audience**: Game engine engineers who need to add new state, understand reactivity, or extend `ClientState` for DM features or core improvements.

## Core Idea

`ClientState` is the **single reactive source of truth**.

- Defined in `korangar/src/state/mod.rs`.
- Derives `RustState`, `StateElement`, `StateWindow`.
- UI and other systems bind to **paths** (e.g. `client_state().hotbar()`).
- Changes are made with `follow_mut(path)` and applied at the end of the frame via `apply()`.
- This enables automatic UI updates without manual dirty flags.

## Key Files

- `korangar/src/state/mod.rs` — Main `ClientState` struct + path extension trait.
- `korangar/src/state/*` — Sub-modules (inventory.rs, skills.rs, status_effects.rs, hotbar.rs, theme/, etc.).
- `korangar-interface/src/element/state.rs` — `StateElement` trait.
- `rust_state` crate (external dependency) — Provides `Path`, `RustState` derive, `follow`, `follow_mut`.
- Usage sites:
  - `src/lib.rs` — Network events mutate state.
  - Window constructors — e.g. `StatusBarWindow::new(client_state().status_effects())`.
  - Inside windows — `state.get(&path)` for reads during layout.

## How Reactivity Works

1. `ClientState` fields are wrapped (or accessed) through path types generated by derives.
2. When you do:
   ```rust
   let effects = self.client_state.follow_mut(client_state().status_effects());
   effects.apply(...);
   ```
3. The mutation is recorded.
4. At end of frame (`lib.rs`):
   ```rust
   if let Err(errors) = self.client_state.apply() { ... }
   ```
5. Any UI element whose layout depends on that path is re-laid-out and re-rendered.

This is why adding a new field to `ClientState` (even hidden) and deriving the traits makes it immediately usable from UI.

## Adding New State (Recommended Pattern)

For DM features, follow the isolation rule (see `DM_CLIENT_IMPLEMENTATION.md`):

```rust
// In ClientState
#[hidden_element]
dm_state: DmState,

// In a new dm/state.rs
#[derive(Default, RustState, StateElement)]
pub struct DmState {
    pub initiative: Vec<InitiativeEntry>,
    pub last_checks: VecDeque<CheckResult>,
    // ...
}
```

Then provide a path helper (pattern used in `ClientStatePathExt`):

```rust
// In state/mod.rs or dm mod
pub fn dm_state() -> impl Path<ClientState, DmState> { ... }
```

In windows:
```rust
DmCheckConsole::new(client_state().dm_state())
```

Inside the window's layout code you can `state.get(&self.dm_path)`.

## Existing State Modules (Examples)

- **status_effects.rs** — Recent clean example. Has `apply`, `remove`, `tick`, `clear`.
- **inventory.rs** — More complex (async metadata loading).
- **hotbar.rs** / **skills.rs** — Slot-based with lookup into library.
- **theme/** — Two themes (menu / in-game) + world theme.

Use these as templates when adding new reactive data.

## Important Methods & Patterns

- `follow(path)` — immutable borrow via path.
- `follow_mut(path)` — mutable.
- `try_follow(path)` — Option version.
- `clear()` on map change / disconnect (almost every list does this).
- `#[hidden_element]` — Keeps it out of the main state inspector unless wanted.
- `StateWindow` derive — Allows the debug state inspector window.

## Data Flow Examples

**Network → State**:
```rust
NetworkEvent::AddQuestEffect { quest_effect } => {
    // ...
    self.client_state.follow_mut(...).something();
}
```

**Input → State**:
```rust
// In process_user_events or similar
*self.client_state.follow_mut(client_state().buffered_action()) = Some(...);
```

**State → UI**:
Window holds a `Path<ClientState, TheState>` and reads in `create_layout_info` / `lay_out`.

## Gotchas for Engineers

- Mutations must go through `follow_mut` + `apply()` — direct field access usually doesn't trigger reactivity.
- State is applied **after** rendering decisions in some cases — be careful with ordering.
- Large `Vec`s (entities, chat) are cleared on map change to avoid stale data.
- For high-frequency data (initiative ticks, hazard state), consider a per-frame `tick()` method called from `lib.rs`.
- DM state should live under one `dm_state` field for easy isolation and clearing.

## How to Add a New Reactive Feature (Step by Step)

1. Define struct with derives in appropriate module (or `src/dm/state.rs`).
2. Add field to `ClientState`.
3. Add path accessor (follow pattern from existing code).
4. Wire mutations from network events or input.
5. Add `clear()` logic on map change if appropriate.
6. Create or extend a window that binds to the path.
7. Add to debug inspector if useful (`StateWindow`).

See `status_effects.rs` + `status_bar.rs` + the recent `NetworkEvent::StatusChange` handling as a minimal end-to-end example.

## Relation to DM Work

All DM features (dice results, initiative, hazards, flags, downed state) are intended to live in `dm_state`. This keeps the core `ClientState` relatively clean for upstream rebases.

For the full picture of adding DM state, read `DM_CLIENT_IMPLEMENTATION.md`.

This guide + reading `state/mod.rs` + one sub-module + one window that uses it should give an engineer enough to extend the reactive system confidently.
