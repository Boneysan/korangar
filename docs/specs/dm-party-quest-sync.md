# DM Session party quest synchronization — GDD §8 / S10

**Decision (2026-09-23):** A player who joins the active campaign party late automatically inherits that party's campaign quests and story progress. This catch-up includes story flags, but does not grant past rewards. Characters remain separate; another character on the same account inherits nothing until it joins the party. General discoveries and non-story unlocks remain account-wide under GDD §9.6.

## Current implementation (source audit 2026-09-24)

- `OnPCPartyJoin` calls `DM_CheckpointSyncSelf` and `DM_CatchUpFromParty` immediately while the active campaign session is allowed. This is the automatic late-join hook.
- `OnPCQuestLog` catches up after the server restores the character's saved quest list. `OnPCLoginEvent` intentionally waits for that point; `OnPCLoadMapEvent` retries after party/map context is available. Returning party members therefore use the same status reconciliation path.
- `DM_PartyApplyQuest` and `DM_PartyApplyFlag` append typed `quest_set`, `quest_complete`, `quest_erase`, `flag_set`, or `flag_clear` rows to `dm_campaign_party_event` before mutating character state. `DM_ReplayPartyEvents` reads rows in ID order, applies only those types, verifies the quest/flag postcondition, and advances `dm_campaign_party_cursor.last_event_id` for that character only after verification. It never handles rewards.
- Replay runs on the existing forced join/quest-log catch-up path and map-load retry. Latest-state `dm_campaign_party_state` snapshot reconciliation and the explicit quest/flag allowlist remain as a backfill path for state written before event journaling; they do not replace new journaled transitions.
- Catch-up does not replay campaign rewards. `DM_ClaimPendingGrants` is a separate character-keyed queue for grants explicitly queued to an existing character, such as while offline.
- The checkpoint, state/grant, and event/cursor tables are declared in indexed Hercules upgrades `2026-09-24--19-45.sql` through `2026-09-24--19-47.sql`; the integration runner applies these upgrades to its disposable schema before starting the servers. The event tables are also created idempotently by the DM event NPC at startup. Run identity remains the fixed campaign namespace plus party ID; party re-creation migrates the journal when no destination checkpoint exists, and explicit reset clears the journal/cursors. A separate run UUID and repair/preview UX are not implemented. `dm_campaign_checkpoint_*` variables in `dm_checkpoint.txt` are unprefixed Hercules character variables (the SQL member row is also keyed by character ID); the older claim that these mirrors were `#` account-scoped was incorrect.

Source-side typed replay is partially verified. Live `dm-party-offline-replay` starts a campaign quest and sets a story flag while one enrolled member is disconnected, confirms both states on that character's return, then forces catch-up again and verifies the quest is not duplicated. This covers one same-party reconnect path only; late join, alternate-character isolation, quest completion/erase ordering, party recreation, reward isolation, and failed-replay repair remain open.

## State and eligibility

- The durable ordered **party campaign event log** now uses a unique SQL ID plus campaign and party identity. Events store type (`quest_set`, `quest_complete`, `quest_erase`, `flag_set`/`flag_clear`), quest ID or allowlisted story-flag name, value, actor character ID, and timestamp. A checkpoint *step* remains distinct from event ID: several quest actions can occur between steps. Events are emitted only by server-side campaign state helpers, never narrative chat or client packets.
- Keep an **enrollment record and applied-event cursor per character ID** for that campaign run. Existing `dm_campaign_checkpoint_member` is a starting point but needs an enrollment sequence and per-character cursor (or companion table). When a character joins an active campaign party, automatically enroll it and catch it up to the party's current quest and story state. A temporary disconnect does not unenroll the character. Do not auto-enroll another character merely because its account has a character in the party. Preserve identity across party re-creation without merging two different campaign runs.
- Story quest log, story flags, chapter completion, and story-gated access live on the **character**. Do not use `#` or `##` variables for them or for the per-character checkpoint mirror. Prefer character variables without a prefix or query the character-keyed SQL cursor for display. The party checkpoint coordinates the group; it is not proof that a particular character completed a chapter.
- While a run is active, apply an event immediately to every enrolled online character in the party. A late joiner receives the current campaign quests and story flags as part of joining; do not replay or duplicate past rewards. A temporarily offline party member catches up on reconnect.

## Mutation and recovery contract

**Current source contract:** Route DM campaign quest/flag writes through `DM_PartyApplyQuest` / `DM_PartyApplyFlag`. Log the typed event before the actor's per-character mutation; replay in sequence and advance that character's cursor only after the postcondition is verified. `quest_set` leaves an existing active/completed quest intact; `quest_complete` ensures the quest exists before completing it; `quest_erase` removes it if present; flag events set the explicit value in order. Replay is idempotent. Event-write failure prevents the actor's mutation and reports an error. Multi-member transactional rollback and a DM preview/repair UI are not implemented.

The current login, map-load, and party-rejoin hooks now replay a missing event range, then retain snapshot catch-up for legacy state. There is not yet an `@dm reconcile preview/confirm` workflow: run UUID, ahead-of-party divergence reporting, and explicit audited repair remain target work. Never rewind a character who is ahead or overwrite a different run. The client quest log gets its normal server quest-list packets after server reconciliation; `[DMJ]` is presentation, not authority.

Rewards are **not** replayed by quest/flag catch-up. A later reward repair must use stable once-per-character grant keys and an audited preview so reconnect/retry cannot duplicate EXP, Zeny, or items. Personal inventory hand-ins remain attached to the handing-in character.

## Acceptance (partial live verification)

1. Two online enrolled characters receive the same DM quest start/complete/erase and branch flag, each in their own quest/character state; neither needs to be the NPC speaker or kill owner.
2. **Partially verified:** one enrolled character disconnects before a quest start and flag change. On return to the same party/run, both state changes arrive; a repeated catch-up does not emit a duplicate active quest notification. Multiple transitions, complete/erase ordering, and cursor-level checks remain.
3. **Source hooks present; session check open.** A late joiner receives the party's campaign quests and story flags, without duplicate or retroactive rewards. A second character on the same account receives that catch-up only after it joins the party.
4. Party re-creation preserves an enrolled character's run identity and cursor without copying progress to a different character or merging unrelated runs. Ahead/failed/missing-event cases are reported, not silently overwritten.
5. A failed event write leaves all characters unchanged; a failed per-character apply leaves its cursor behind so retry repairs it. Quest/flag sync never duplicates a reward, and normal non-DM quests remain untouched.

Check the SQL migration in isolation, run the campaign script checker and `map-server --run-once`, then perform a live two-client/character-switch test. Existing static checks for `dm_checkpoint.txt` alone do not prove quest replay or character isolation.
