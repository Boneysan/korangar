# GDD improvement plan — end-to-end delivery map

**Scope:** [GDD v0.2](../GDD.md) §§2–19, including decisions through 2026-09-22. This is the single planning map for **all in-scope GDD improvements**, not a claim that every feature is built or fully specified. The [next-slices plan](gdd-next-slices.md) is Wave 1's executable detail: client 1–15, server S1–S10, current-code audit, dependencies, and live acceptance. This document owns the remaining queue, sequencing, and coverage. Do not work from unchecked boxes in `PROJECT_PLAN.md`, `FEATURE_ROADMAP.md`, or historical handoffs as if they were a competing priority list.

**Status vocabulary:** *Built* means code/config exists, not necessarily live-verified. *Planned* means the implementation boundary and acceptance are defined below; the cited specification or a slice-start code audit still resolves exact files. *Conditional* means a named evidence/owner gate must pass before implementation. *Excluded* is an explicit GDD scope decision. No date or staffing commitment is implied by the order.

## Non-negotiable product contracts

- Preserve recognizable RO combat, six-stat/class asymmetry, click-to-move, server authority, useful ground control, rare drops, and ordinary world travel. No universal dodge/iframe, forced rotation, giant permanent telegraphs, unrestricted world-map teleport, player vending/auction, or mandatory story gates on ordinary hunting areas (§§3–6, 9, 11–12).
- General discoveries and non-story access are **account-wide**. Story quests, choices, chapters, story-gated access, and rewards are **per character**. DM Session state is character-owned; joining the active campaign party grants that character the party's current quests and story flags, but no past rewards. Same-account alternates receive the state only after they join (§§2.3, 8, 9.6).
- The Adventure Guide is open and searchable for verified gameplay facts from a fresh account. Discovery badges do not hide build data. Campaign spoilers and DM-only controls have separate authorization (§9.5–9.6).
- Ordinary players can reset stats and skills separately, free at every level. S2 repairs the existing command/permission/UI mismatch (§7.5).
- The Seal Cascade campaign is DM Session mode, **not** the self-directed story spine. Reuse shared infrastructure, not its completion flags or plot as a shortcut (§§2.3, 8.1).

## Delivery sequence and release gates

| Wave | Delivery boundary | Required evidence before calling it complete |
|---|---|---|
| 0 — baseline and safety | Keep the playable fork stable; resolve S1/S2 and the G0–G4 readiness checks; start F36's measurement baseline before changing AI, bosses, or economy. | Normal-player permissions and reset controls verified; generated data revision matches Hercules; UI/live observations recorded. |
| 1 — first useful client | Deliver [1–15 and S1–S10](gdd-next-slices.md) in dependency order, not as one release. Ship small groups: combat readability; navigation/data; player Guide; party/quest/HUD; accessibility; DM reconnect correctness. | Each slice's acceptance passes; two-client and character-switch tests for cross-fork changes; Guide works before discovery sync. |
| 2 — complete comprehension | Finish server-derived reference coverage, build preview/planner, world/map overlays, contextual combat explanations, and UI linking (F01–F13 below). | A new player researches a build and reaches a named dungeon without an external wiki; unsupported fields are explicitly unknown, not guessed. |
| 3 — deepen play and story | Expand monster families, elites, MVPs, self-directed story, DM act quality, and party coordination (F14–F26, F39). | Pilot maps and first boss pass mixed-party sessions; story progress remains per-character; group sync and safe catch-up are demonstrated. |
| 4 — economy and long-term polish | Tune loot/refinement/economy, build crafting/commission only after demand, complete social/UI polish, performance and administration (F27–F38). | Before/after telemetry and player feedback support tuning; no duplication/loss in trade or commissions; accessibility and frame-time budgets hold in crowded fights. |

The wave numbers are dependency stages, not a requirement to finish every row of one wave before an independent row in another. A row may be split into several PRs; every PR states which row and acceptance subcase it closes. No row is marked *Built* merely because a design or JSON filename exists.

## Definition of done and maintenance

Every implementation row needs: (1) a slice-start re-audit of the target branch, (2) a named client/server owner and any schema/packet migration, (3) focused unit/data tests and a live player scenario, (4) regression for the account-general versus character-story split where relevant, (5) updated Guide/server provenance if rules change, and (6) an updated GDD Appendix E status with revision/date. For visual work, capture the [wireframe pack](../specs/gdd-ui-wireframes.md) states at small/default/high-DPI sizes. For server scripts, run the script checker and map-server startup parse; for C changes, build and run a live 20220406 client/headless scenario.
