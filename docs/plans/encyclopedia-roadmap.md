# Adventure Guide encyclopedia completion plan

**Parent:** [GDD §9.5](../GDD.md#95-adventure-guide--the-in-game-encyclopedia). [Coverage inventory](encyclopedia-coverage.md) records what exists today; [data contract](../specs/encyclopedia-data.md) defines the export and client rules. This plan orders the remaining work and defines when a reference area is useful enough to call complete.

For the iterative Qwen3 workflow across all E0–E7 packages, see the [local model plan](encyclopedia-local-model-plan.md) and its [resume ledger](encyclopedia-qwen3-progress.json). It requires source-grounded validation and the release gates below.

## Goal and release rule

A fresh, non-DM account can answer three practical questions inside the game: **What does this do? Where can I get or use it? What conditions change the answer?** It can follow links among items, cards, monsters, maps, NPCs, quests, skills, statuses, jobs, and mechanics. Build information is available before discovery. Campaign spoilers and DM controls stay outside the general reference.

An area is complete only when its supported fields have player-readable explanations, source-backed links, visible limits, and a checked client presentation. A row of IDs, raw script calls, or a generated JSON file is evidence for work, not completion. Dynamic behavior may remain unknown if the Guide says so plainly and offers the best verified static answer.

## Evidence and presentation contract

Every player-facing claim has a stable entity ID, source revision, path/record or reviewed source location, and one of these evidence states:

| State | Meaning in the Guide | Typical example |
|---|---|---|
| Verified | The loaded data or reviewed control flow establishes the claim for this server. | A literal monster drop rate from the active DB; a quest reward checked through its completion branch. |
| Conditional | The claim is supported, but a known prerequisite, branch, timer, or runtime variable changes it. Display that condition. | An exchange offered after a quest flag; a boss summoned by an event. |
| Configured estimate | The source defines a base rate, spawn amount, or formula input; runtime modifiers may change the observed result. Display units and modifier caveat. | Monster drop base rate; configured spawn count. |
| Source clue | A call site or proximity suggests a relationship, but the path to it has not been reviewed. Keep it searchable as a clue and do not call it a reward, service, or accessible spawn. | Nearby `getitem`, `checkquest`, or `monster` call. |
| Not reviewed | Relevant source exists but no semantic review has established the effect or flow. | An untranslated item script or unknown NPC role. |
| Unknown | Source is absent, dynamic, unavailable to the client, or not yet extracted. Give a specific reason when known. | Live spawn population or a runtime map flag with no observed state. |

Provenance applies to individual assertions, not just the entry as a whole. A verified NPC coordinate does not verify its service, and a verified quest giver does not verify every branch or reward. Keep authored explanation records separate from generated facts and cite the exact source and revision they explain. Reject stale citations during regeneration. Do not publish raw internal flags or rates as unexplained player prose.

At minimum, a reviewed assertion record needs: entity kind and stable ID; claim kind; player-facing value or explanation; evidence state; source repository/revision/path and record or line anchor; applicable condition/branch; reviewer and review date; and related entity IDs. Include an explicit scope such as “loaded renewal scripts only” when the scan does not cover all server content. Generated facts may point to the exact DB record instead of a human reviewer, but still carry the data revision.

### Execution sequence

1. **E0 first:** establish the evidence and counting model before adding more inferred links.
2. **E1 then E2:** convert the existing grant/removal/shop/NPC indexes into confirmed player actions. This gives the fastest improvement to “where do I get/use it?” and supplies a review pattern for quest rewards.
3. **E3 and E4 as paired slices:** an item or skill translator often depends on understanding the same status or formula implementation. Publish small reviewed patterns instead of widening the allowlist based on syntax alone.
4. **E5 and E6 by player journey:** prioritize quests and maps connected to the reviewed acquisition and effect records; do not wait for all 3,172 quest IDs or all dynamic spawns to be solved before shipping a useful partial page.
5. **E7 after the source reviews:** the fresh-account client pass is deferred until the remaining E1, E4, and E5 reviews above are done. Run it once before calling the encyclopedia excellent. Do not treat an automated build as that pass.

Each package can ship in small batches. Mark a package **in progress** while it has known unreviewed coverage, **partial** when its first complete vertical slice passes but breadth remains, and **complete** only when its exit check passes for the declared scope. State the scope and denominator whenever a percentage or count is reported.

## Completion checklist

Call the encyclopedia **excellent for the declared server revision** only when all of these are true:

- Every category in the coverage inventory has a named status, a source revision, and a next step or a reason its remaining fields are unknowable.
- Common player questions have connected answers: effect, requirements, acquisition/use, location, conditions, and what to do next.
- Item/card/skill explanations distinguish exact behavior from estimates and state known chance, duration, scaling, target, and condition details.
- Quest instructions identify verified giver/turn-in and all supported prerequisites, objectives, branches, rewards, and repeat rules; gaps are visible per stage.
- Monster and map pages distinguish DB facts, configured static directives, script clues, conditional behavior, and live observations.
- NPC pages explain verified roles, stock/cost, availability, and reachability; bare declarations are not described as services.
- Formulas and rules cite active source/config precedence and include checked examples; unresolved runtime changes are labeled.
- Search and reciprocal links let a player move among all of the above without dead ends. Fresh-account visibility does not depend on discovery or DM permissions.
- The export pipeline catches stale reviewed citations, schema/revision mismatches, and dangling required links; a representative sample is checked against source and the running server.
- A recorded new-player acceptance pass completes representative acquisition, build-research, quest, and navigation journeys. The result includes failed searches and corrections, not only successful examples.

## Implementation and quality loop

For each batch: collect from **loaded** Hercules config/scripts and server code; normalize stable IDs and links; review conditions and provenance; generate versioned data; render it in the player Guide; compare representative entries to source and the running server; update the coverage inventory. Exporters should be deterministic and reject duplicate IDs, unresolved required links, stale reviewed citations, and revision mismatches. A live observation is needed before claiming runtime behavior, service availability, or route usability.

Track progress with field coverage, not one overall percentage: translated effects, fully explained effects, verified acquisition paths, reviewed quest stages, verified NPC roles, classified spawn calls, explained map rules, and reviewed skill/status/formula pages. Record denominators and source revision with every report. Count conditional and unknown cases separately so a larger index cannot masquerade as better verified guidance.

For every new reviewed data family, retain one small source fixture or citation-validation case that exercises its important branches (for example, success/failure exchange, quest prerequisite/reward, map override, or status duration). Prefer exporter-level validation of real source references over hand-maintained counts. Do not count a generated row as reviewed unless its source semantics were checked.
